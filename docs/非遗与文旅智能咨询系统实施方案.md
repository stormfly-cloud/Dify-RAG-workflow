# 非遗与文旅智能咨询系统实施方案

## 1. 总体方案

- 采用独立业务系统包住自托管 Dify，不修改 Dify 源码。
- Dify 负责知识库、文档索引、向量检索和模型调用。
- 业务系统负责管理员权限、知识库映射、发布控制、用户、积分、支付和跨端体验。
- 技术栈采用 TypeScript Monorepo：
  - PC 用户端与管理员后台：Next.js
  - 服务端 API：NestJS
  - 移动 H5 与微信小程序：Taro React
  - 数据库：PostgreSQL
  - 队列与缓存：Redis、BullMQ
- 管理后台使用 Ant Design，突出高密度表单、表格和状态可视化。
- 单机构单 Dify 工作区。
- 每个业务知识库与一个 Dify Dataset 一对一映射。
- Dify 密钥仅保存在服务端。
- 首版范围：
  - 文件、粘贴文本和 FAQ 入库
  - 两级管理员
  - 手机号、微信登录
  - 微信支付积分包
  - 流式问答、引用、多轮会话、历史、反馈和重新生成
  - 暂不实现网页抓取、Notion/飞书连接器和多模态问答

## 2. Dify 集成边界

- 通过稳定 Knowledge Service API 完成知识库创建、更新、删除、模型查询、文件/文本上传、索引进度轮询、分段管理、元数据、标签和召回测试。
- 每个 Dataset 自动创建 `app_publish_state` 元数据字段。
- 文档索引完成后先标记为 `draft`。
- 用户检索时强制过滤 `app_publish_state=published`，实现业务侧的审核发布和撤销发布。
- 问答不依赖 Dify App 的静态 Dataset 列表：
  - 后端先按用户选择的知识库调用 Dify `/datasets/{id}/retrieve`
  - 多库查询使用 Reciprocal Rank Fusion 合并结果
  - 再将上下文和引用交给一个一次性导入的 Dify Chatflow Generator App 生成流式回答
- 仓库提供版本化 Chatflow DSL。
- 初始化时由管理员在 Dify 控制台导入并发布一次。
- App 接收 `context`、`citations_json`、`knowledge_scope` 等输入，不直接绑定知识库。
- 后续新增知识库无需修改 Dify App。
- Dify 创建 Dataset 需要全知识库范围的 Service API Key，因此使用一个服务端全量 Knowledge Key。
- App API Key 独立配置。
- 两类密钥加密存储、禁止下发前端、禁止写入日志。
- 不依赖 Dify 私有 Console API。
- 公开接口未提供的原生精确分段估算预览不做逐像素复制：
  - 界面展示处理配置和本地预估
  - 索引后的真实分段以 Dify 返回结果为准

## 3. 核心实现

### 3.1 知识库创建

知识库创建向导分五步：

1. 基础信息与标签
2. 索引方式与嵌入模型
3. 分段模式与处理规则
4. 检索与重排配置
5. 来源上传与确认

支持：

- `high_quality/economy`
- `text_model/qa_model/hierarchical_model`
- 自动/自定义分段
- 分隔符、最大 Token、重叠 Token
- 父子分段
- 摘要索引
- 召回方式、Top K、阈值
- 重排模型和混合检索权重

### 3.2 文档处理状态机

统一状态：

`uploading -> queued -> parsing -> cleaning -> splitting -> indexing -> review_required -> published`

异常状态：

- `failed`
- `paused`
- `archive`
- `disabled`

后台 Worker：

- 轮询 Dify
- 按指数退避处理 `429/503`
- 通过 SSE 将阶段、分段进度、时间和错误实时推送至管理界面

管理员能力：

- 批量上传
- 查看文档和 Batch 进度
- 查看真实分段
- 编辑分段或 FAQ
- 启停分段
- 配置元数据
- 执行召回测试
- 重试失败任务
- 审核发布、撤销发布和归档

重新索引规则：

- 已发布文档发生内容、分段或处理规则变更时，先撤出检索。
- 触发重新索引。
- 完成后重新进入审核状态。
- 避免旧内容继续被回答。

### 3.3 数据模型

业务 PostgreSQL 保存：

- 用户
- 管理员角色
- 知识库映射
- 文档
- 任务事件
- 分段索引映射
- 会话
- 消息
- 引用
- 模型用量
- 订单
- 支付
- 不可变积分账本

原始文件由 Dify 存储。

业务库只保存：

- 校验值
- Dify ID
- 必要元数据

### 3.4 积分计费

- 采用整数微积分账本。
- 管理端配置每千输入 Token、每千输出 Token 对应的积分数。
- 请求前按上下文估算值和最大输出 Token 预授权。
- 收到 Dify `message_end.metadata.usage` 后按实际用量结算并释放差额。
- 生成失败释放预授权。
- 禁止余额透支。

### 3.5 用户与支付

用户侧支持：

- 手机号验证码或密码
- 微信登录
- 账号绑定

安全实现：

- 短信默认接阿里云短信
- 密码使用 Argon2id
- 浏览器使用 HttpOnly 安全 Cookie
- 小程序使用短周期访问令牌和刷新令牌

微信支付 V3 统一封装：

- PC Native 扫码
- 微信内 JSAPI
- 小程序支付
- 异步回调

订单、支付单、退款和积分流水全部幂等。

积分包价格和积分数量由超级管理员配置。

### 3.6 对外接口

接口领域：

- `/admin/knowledge-bases`
- `/admin/ingestion-tasks`
- `/admin/documents`
- `/admin/retrieval-tests`
- `/auth`
- `/chat`
- `/credits`
- `/orders`
- `/payments/wechat/notify`

统一提供：

- OpenAPI
- Zod/TypeScript 类型
- Taro 共享 SDK

### 3.7 安全措施

- 管理员操作审计
- RBAC
- 请求限流
- 文件魔数校验
- 格式与大小限制
- 恶意文件扫描
- Dify 错误脱敏
- 提示词注入防护
- 统一内容安全兜底
- 敏感配置隔离

## 4. 部署与验证

新增独立服务：

- `app-api`
- `app-worker`
- `app-web`
- `app-admin`
- `app-miniapp`
- `app-postgres`
- `app-redis`

通过独立 Compose 文件加入现有 Docker 网络。

复用现有 Nginx 作为统一入口，不共享 Dify 数据库表。

默认域名：

- `www.<domain>`
- `m.<domain>`
- `admin.<domain>`
- `api.<domain>`
- `dify.<domain>`

Dify 控制台限制为管理员 IP 或 VPN。

HTTPS 使用 Let's Encrypt 自动签发。

SSE 代理关闭缓冲并延长读取超时。

首版容量：

- 4 核 8GB
- 约 100 并发
- 1 万文档

Redis 队列限制索引轮询和模型请求并发。

Dify、PostgreSQL、Redis、应用均配置健康检查和持久化卷。

### 4.1 测试范围

- Dify 客户端契约
- 知识库创建
- 索引阶段
- 失败重试
- 重复上传
- 元数据发布过滤
- 分段编辑
- 多库检索
- 引用
- Token 预授权与结算
- 支付回调重放
- 退款
- 管理员权限

### 4.2 跨端测试

- Playwright 验证 PC、移动 H5 管理流程及桌面/移动视口。
- 微信开发者工具验证 Taro 登录、支付和问答。

### 4.3 端到端验收

创建知识库

-> 上传文档

-> 实时看到完整索引过程

-> 审核分段

-> 发布

-> 用户跨端咨询并获得带引用回答

-> 微信支付并正确扣分

## 5. 实施顺序

1. 基础设施与账号体系
2. 知识库创建与索引可视化
3. 问答与积分
4. 微信小程序与支付
5. Linux Compose 部署和压测验收

上线前必须准备：

- Dify 模型供应商
- 域名和 HTTPS
- 短信账号
- 微信开放平台/小程序 AppID
- 微信支付商户号及 API v3 证书

## 6. 默认假设

- Dify 工作区已配置可用的 LLM、嵌入和可选重排模型。
- 具体模型不在代码中硬编码，由管理员界面从 `/models/model-types/{type}` 动态加载。
- 首版文档单文件上限沿用 Dify 默认 15MB，可运维调整。
- 公网运营需完成 ICP、隐私政策、用户协议及文旅内容审核规则。
- 微信支付和短信在本地开发环境使用模拟适配器，生产环境切换到真实商户与短信凭证。
